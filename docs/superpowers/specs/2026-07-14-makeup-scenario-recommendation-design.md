# 메이크업 시나리오 추천 설계

작성일: 2026-07-14

## 현재 구현 결정

- 사용자 요청에 따라 얼굴 분석 및 퍼스널 컬러 데이터 반영은 현재 비활성화한다.
- 모바일에서 `내 분석 결과 반영` 옵션을 노출하지 않고, 추천 API 요청에도 분석 데이터를 보내지 않는다.
- 상황과 질문은 Claude Haiku 4.5, 세 가지 추천 결과는 Claude Sonnet 4.6, 각 결과 이미지는 OpenAI Image로 생성한다.
- 추천과 재조정 결과는 사용자 소유 보고서로 저장하며, 재조정 보고서는 원본 보고서를 참조한다.

## 1. 목적

사용자가 정형화된 카테고리를 고르는 대신 재미있는 문구를 구경하며 자신이 원하는 메이크업을 발견하게 한다. 선택한 시나리오와 자유 입력, 기존 얼굴 분석 및 취향 데이터를 바탕으로 AI가 필요한 정보만 추가로 질문한 뒤 다음 세 가지를 함께 추천한다.

- 완성 메이크업 룩
- 부위별 메이크업 방법
- 사용할 제품과 대체 제품

첫 화면의 성공 기준은 가장 빠른 검색 시작이 아니라, 사용자가 문구를 탐색하다가 자신에게 끌리는 장면과 분위기를 발견하는 것이다.

## 2. 설계 원칙

- 첫 화면은 선택 폼이 아니라 스크롤 가능한 메이크업 아이디어 피드로 보이게 한다.
- `데일리`, `스페셜`, `유니크` 같은 큰 카테고리를 첫 진입의 필수 선택으로 사용하지 않는다.
- 상황극, 장난스러운 문구, 프리미엄 문구를 섞되 각 문구의 의미는 명확해야 한다.
- AI는 프롬프트와 기존 사용자 정보에 이미 있는 내용을 다시 묻지 않는다.
- 추가 질문은 보통 1~2회, 최대 3회로 제한한다.
- 선택지로 표현되지 않는 답은 모든 질문에서 자유롭게 입력할 수 있다.
- 마지막 질문에서는 별도 턴을 만들지 않고 `+ 조건 추가`를 펼쳐 추가 요청을 함께 제출할 수 있게 한다.
- 결과는 하나의 정답이 아니라 안전한 선택, 더 과감한 선택, 예상 밖의 발견을 함께 제공한다.
- 사용자가 직접 작성한 최신 요청을 AI 추론이나 과거 취향보다 우선한다.
- 다른 팀원이 소유한 아우라딘 구현은 수정하거나 런타임 의존성으로 결합하지 않는다. 개발 및 QA에서는 동일 조건의 결과를 비교하는 선택적 provider로만 사용할 수 있다.

## 3. 첫 화면: 메이크업 시나리오 발견

### 3.1 화면 구조

상단에는 제목과 자유 입력창을 둔다. 입력창 아래에는 작은 체크 옵션으로 분석 정보 사용 상태를 표시하고, 그 아래에는 30~36개의 시나리오 문구를 퍼즐 형태로 노출한다. 자유 입력 CTA는 스크롤 내용과 분리해 화면 하단 safe area 위에 플로팅으로 고정한다. 키보드가 열리면 CTA는 키보드 위로 이동하며, 입력이 비어 있으면 비활성 상태다.

```text
어떤 모습이 끌리나요?

[ 원하는 느낌이나 상황을 직접 들려주세요 ]
[✓ 내 분석 결과 반영]

지금 끌리는 한 문장

[ 성수동 감성 느좋 룩 ] [ 홍대 4번 출구 서브컬처 룩 ]
[ 음악프로그램 무대 접수 아이돌 룩 ] [ 말없이 완승 ]
[ 출근길 자주 마주치던 사람에게 먼저 인사하는 날 ]
...

                  [ 내 이야기로 추천받기 ]  ← 하단 고정
```

첫 뷰포트에는 6~10개가 보이고 나머지는 자연스럽게 스크롤한다. 칩은 고정 2열이나 단순 `flexWrap`을 사용하지 않는다. 서로 다른 폭, 높이, 글자 크기와 색을 가진 칩이 남는 공간을 채우는 퍼즐형 dense layout으로 배치해 잡지의 헤드라인처럼 리듬을 만든다.

`내 분석 결과 반영`은 부가 설명 없는 작은 체크 옵션이다. 선택된 분석 리포트가 있으면 기본 체크하고, 없으면 비활성 체크박스와 동일한 짧은 레이블만 유지한다. 접근성 role은 `checkbox`이며 전체 옵션 영역을 눌러 상태를 바꿀 수 있다.

### 3.2 문구 구성

한 세션에서 보여주는 30~36개는 다음 출처를 혼합한다.

- 검수된 기본 문구: 30%
- 상황극 및 캐릭터 문구: 25%
- 사용자 취향 기반 개인화 문구: 20%
- 계절, 시간대, 운영 중인 트렌드 문구: 15%
- 평소와 다른 도전 및 AI 와일드카드: 10%

카피 결은 다음 유형을 혼합한다.

- 에디토리얼형: 장소와 문화적 분위기를 짧고 선명하게 표현한다.
- 장면형: 카메라가 켜진 듯 구체적인 순간을 제시한다.
- 짧은 독백형: 사용자의 마음을 대신 말하되 동일한 종결을 반복하지 않는다.
- 서사형: 앞뒤 이야기가 궁금해지는 한 장면을 만든다.
- 캐릭터형: 성별이 아니라 취향과 태도로 인물을 그린다.

기본은 에디토리얼형으로 두고 장면형과 캐릭터형으로 세계를 넓힌다. 짧은 독백형과 서사형은 감정적으로 걸리는 지점에 일부 섞는다. `오늘`, `~할 거야`, `~해볼래`는 시간성과 독백이 꼭 필요한 문장에서만 사용하며 반복하지 않는다. `여신`, `남신`, `고명딸`처럼 특정 성별을 전제하는 호칭은 기본 시나리오에서 제외한다. 첫 6개 안에는 최소 세 가지 카피 유형이 포함되어야 한다.

### 3.3 대표 문구 예시

```text
성수동 감성 느좋 룩
홍대 4번 출구 서브컬처 룩
이태원 해방촌 힙스터 룩
한남동 갤러리 프리뷰 룩
음악프로그램 무대 접수 아이돌 룩
SNS에 저장만 해둔 그 룩, 이번엔 직접
공항 출국 사진 레전드 룩
전 애인 결혼식, 말없이 완승
출근길 자주 마주치던 사람에게 먼저 인사하는 날
야구장 전광판에 잡히고 싶은 날
새벽까지 살아남는 페스티벌 헤드라이너 룩
부잣집 고명자식 음대생 룩
느낌 좋은 미대생 전시 오프닝 룩
첫 출근인데 이미 에이스
점 하나 찍고 완전히 달라진 서사
사진과 영상에서 확실한 존재감
5분 만에 완성한 정교한 인상
낯설지만 분명히 나다운 변화
```

강한 연애나 복수 서사는 전체의 일부로만 사용한다. 외모 비하, 불안 자극, 신체 변화 보장, 타인에 대한 혐오 표현은 생성하거나 노출하지 않는다.

### 3.4 문구 데이터 모델

화면 문구와 실제 추천 입력을 분리한다.

```ts
type MakeupScenarioPrompt = {
  id: string;
  displayText: string;
  seedPrompt: string;
  intentTags: string[];
  tone: 'narrative' | 'playful' | 'premium';
  copyStyle: 'editorial' | 'scene' | 'monologue' | 'narrative' | 'character';
  visualEmphasis: 'compact' | 'standard' | 'featured';
  palette: 'paper' | 'ink' | 'muted' | 'accent';
  preferredColumnSpan: 3 | 4 | 5 | 6 | 7 | 8;
  source: 'curated' | 'personalized' | 'trend' | 'wildcard';
  personalizationReason?: string;
  expiresAt?: string;
};
```

예를 들어 `5분 했는데 30분 공들인 척`을 선택하면 실제 요청에는 `짧은 시간에 완성할 수 있지만 정교해 보이는 메이크업`이라는 의미가 전달된다. 화면 문구만으로 추천 의미를 추론하지 않는다.

### 3.5 생성과 개인화

전체 검수 문구 풀은 100개 이상 유지하고, 한 번 진입할 때 30~36개를 편집해 제공한다. AI는 새로운 문구를 만들거나 기존 문구를 사용자 말투에 맞게 변형할 수 있지만, 생성 결과는 다음 검사를 통과해야 한다.

- 탭했을 때 추천 방향이 명확하다.
- 같은 의미의 문구가 한 세트에 중복되지 않는다.
- 외모 비하, 민감 정보 추정, 과장된 효능 보장이 없다.
- 반드시 구체적인 `seedPrompt`와 구조화된 의도 태그를 가진다.
- 트렌드 문구에는 만료 시점을 둔다.

생성 실패나 네트워크 오류 시 검수된 로컬 문구 풀을 즉시 사용한다. 첫 화면 진입을 AI 생성 응답으로 막지 않는다.

개인화에는 얼굴 분석 및 퍼스널컬러, 저장한 룩, 최근 선택한 시나리오와 결과를 사용한다. 화면 상단에 `내 분석 결과 반영` 체크 옵션을 표시하고 사용자가 끌 수 있게 한다. 분석 정보는 소프트 선호로만 사용하며 사용자의 현재 요청을 제한하는 하드 조건으로 사용하지 않는다.

### 3.6 퍼즐 칩 레이아웃과 시각 체계

시나리오 영역은 보이지 않는 12열 그리드로 계산한다. 각 칩은 `preferredColumnSpan`과 `visualEmphasis`를 시작점으로 삼되, 실제 글자와 현재 시스템 글꼴 크기를 숨겨진 측정 단계에서 먼저 측정한다. 문장이 필요한 높이보다 작은 칸에 들어가면 세로 점유 칸을 늘리고, 필요한 경우 가로 점유 칸도 늘린 뒤 다시 배치한다.

배치기는 각 칩을 처리할 때 현재 빈 공간 중 들어갈 수 있는 가장 위쪽, 가장 왼쪽 슬롯을 찾아 채운다. 배치 완료 후 화면에 한 번에 표시해 초기 측정 중의 깜빡임을 방지한다. 컨테이너 폭, 시스템 글꼴 배율, 시나리오 세트가 바뀌면 계산을 다시 수행한다.

필수 규칙은 다음과 같다.

- 문구에 말줄임표나 `numberOfLines` 제한을 적용하지 않는다.
- 칩을 고정 2열로 되돌리지 않는다.
- 짧은 문구는 작은 조각, 긴 문구는 더 넓거나 높은 조각으로 확장한다.
- 화면에 표시되는 시각 순서와 접근성 탐색 순서를 일치시킨다.
- 시스템 글꼴 배율이 퍼즐 가독성을 해치는 수준이면 전체 폭 카드 목록으로 전환한다.
- 배치 계산 중에는 기존 높이를 유지하거나 가벼운 skeleton을 표시해 레이아웃 점프를 막는다.
- 칩 전체는 최소 44pt 터치 영역을 확보한다.

색상은 기존 화면과 같은 흑백을 기본으로 한다. 대부분은 `paper`, `ink`, 회색 `muted`를 사용하고, 전체의 일부만 버건디와 옅은 로즈 계열 `accent`를 사용한다. 신규 색은 메이크업 추천 feature-local token으로 제한해 전역 테마나 아우라딘 테마를 변경하지 않는다. 같은 세트에서 강조색이 연속되거나 과도하게 반복되지 않도록 편집한다.

폰트는 세 단계로 섞는다.

- `featured`: 짧고 강한 에디토리얼형 또는 캐릭터형
- `standard`: 장면형과 일반 시나리오
- `compact`: 긴 독백형과 서사형

글자 크기는 시각적 리듬을 위한 것이며 정보 우선순위를 의미하지 않는다. 질문 화면과 결과 화면에는 이 무작위적 크기 변화를 가져오지 않는다.

## 4. 적응형 질문 흐름

### 4.1 질문 결정

시나리오 또는 자유 입력을 받은 AI는 다음 정보가 이미 있는지 판단한다.

1. 원하는 인상과 변화
2. 상황과 장소
3. 도전 강도
4. 시간과 숙련도
5. 예산, 구매 채널, 보유 제품 및 회피 조건

추천 결과에 미치는 영향이 크고 아직 모르는 항목 하나만 다음 질문으로 선택한다. 질문은 보통 1~2회, 최대 3회다. 정보가 충분하면 질문 수를 줄인다.

### 4.2 질문 화면

- 선택지는 4~6개다.
- 선택지는 시나리오 칩처럼 내용 길이에 맞추지 않고 화면 가로 전체를 쓰는 큰 카드다.
- 선택 카드는 검정 배경과 흰색 텍스트로 명확하게 표시한다.
- 진행 상태는 `현재 / 전체` 숫자만 두지 않고 상단의 얇은 segment progress bar로 보여준다.
- 선택지끼리 의미가 겹치지 않아야 한다.
- `AI가 골라줘` 또는 의미상 동등한 위임 선택지를 제공한다.
- 모든 질문 하단에 선택지 대신 사용할 수 있는 자유 입력란을 제공한다.
- 앞선 질문은 선택 즉시 다음 단계로 이동할 수 있다.
- 마지막 질문은 선택 후 바로 이동하지 않고 명시적인 `추천받기` 버튼을 보여준다.

마지막 질문의 기본 구조는 다음과 같다.

```text
어느 정도까지 과감해도 괜찮나요?

[ 조금만 다르게 ]
[ 한눈에 달라 보이게 ]
[ 오늘은 과감하게 ]
[ AI가 골라줘 ]

[ + 조건 추가 ]                         [ 추천받기 ]
```

`+ 조건 추가`를 누르면 같은 화면 안에서 입력창만 펼친다. 새로운 대화 턴으로 계산하지 않는다.

```text
[ 예: 글리터 제외, 립 강조, 15분 이내 ]

                                        [ 추천받기 ]
```

추가 조건은 앞선 선택과 함께 한 번에 제출한다. 빈 입력은 허용하며 추가 설명 문구를 길게 노출하지 않는다.

### 4.3 우선순위

충돌하는 조건은 다음 순서로 처리한다.

1. 안전, 알레르기 및 피부 회피 조건
2. 마지막에 직접 입력한 추가 조건
3. 현재 질문에서 사용자가 직접 선택하거나 작성한 답
4. 최초 시나리오 또는 자유 프롬프트
5. 과거 선택, 저장 기록, 얼굴 분석 및 퍼스널컬러 기반 추론

조건을 지키면서 결과를 만들 수 없으면 조건을 조용히 무시하지 않고 어떤 조건 때문에 후보가 부족한지 알린다.

## 5. 추천 결과

### 5.1 세 가지 룩

결과는 역할이 다른 세 가지 룩으로 구성한다.

1. `anchor`: 얼굴 분석과 현재 요청에 가장 안정적으로 맞는 룩
2. `bold`: 선택한 시나리오를 더 선명하고 과감하게 표현한 룩
3. `discovery`: 평소 취향 밖이지만 어울릴 가능성이 있는 발견형 룩

세 룩은 색상만 조금 다른 중복 결과가 되어서는 안 된다. 각 룩의 차이를 제목과 한 줄 설명으로 분명하게 표현한다.

### 5.2 룩 상세 정보

각 결과는 다음 정보를 제공한다.

- 룩 이름과 대표 이미지
- 이 룩을 추천한 이유
- 반영된 조건
- 베이스, 아이, 브로우, 치크, 립의 부위별 방법
- 단계별 적용 순서
- 예상 소요 시간과 난이도
- 핵심 제품과 대체 제품
- 저장하기
- 기존 AR 가이드로 적용하기
- `더 자연스럽게`, `더 힙하게`, `다른 색으로`, `제품만 바꾸기` 재조정

결과 첫 화면에서는 대표 이미지, 역할, 룩 이름, 한 줄 설명, 핵심 반영 조건, 저장과 AR 적용만 우선 노출한다. 추천 이유, 부위별 단계와 제품 목록은 `자세히 보기`를 눌렀을 때 같은 카드 안에서 펼쳐진다. 카드가 길어지더라도 다른 룩을 먼저 비교할 수 있게 기본 상태는 접힘이다.

MVP의 대표 이미지는 검수된 레퍼런스 룩 이미지 또는 서버가 제공하는 룩 이미지 URL을 사용한다. 사용자 얼굴 합성 이미지를 추천 생성의 필수 조건으로 두지 않는다. 사용자가 룩을 고르면 기존 AR 적용 흐름으로 연결한다.

제품 추천은 새 기능이 소유한 provider 계약을 통해 완성 룩과 조화를 이루는 세트로 제공한다. MVP 기본 provider는 검수된 제품 fixture와 결정적 추천 규칙을 사용한다. 개발 및 QA 빌드에서는 같은 룩 조건을 아우라딘에 보내 결과 품질을 나란히 비교할 수 있지만, 사용자용 기본 흐름은 아우라딘의 가용성이나 변경에 의존하지 않는다.

### 5.3 결과 데이터 모델


## 6. 시스템 경계와 데이터 흐름

### 6.1 모바일 경계

새 경험은 메이크업 룩 추천이라는 독립 기능 경계로 둔다. 새 코드는 `features/makeup-recommendation` 아래에 두고, 공용 `shared` 계층의 테마 토큰, UI 및 `requestBackendJson`만 재사용한다. 아우라딘 전용 디자인 시스템, 타입, 화면, 서비스 또는 상태를 사용자용 기능에서 import하지 않는다.

모바일의 논리 단위는 다음과 같다.

- 시나리오 피드: 문구 로드, 개인화 상태, 새 세트 요청
- 퍼즐 레이아웃: 텍스트 측정, dense placement, 화면 폭 및 글꼴 변화 재계산, 접근성 fallback
- 추천 세션 컨트롤러: 시작, 질문 응답, 조건 추가, 취소 및 만료
- 질문 화면: 선택지, 자유 답변, 마지막 질문의 조건 추가
- 결과 화면: 세 가지 룩, 상세 방법, 제품, 저장 및 AR 이동
- 서비스 계층: `requestBackendJson`을 통한 API 호출과 오프라인 fallback 매핑

구체적인 파일 분할은 구현 계획에서 현재 브랜치의 화면과 라우팅 소유권을 다시 확인한 후 정한다. 새 route를 추가할 수는 있지만 기존 아우라딘 route의 컴포넌트, 파라미터 또는 동작은 변경하지 않는다.

### 6.2 아우라딘 수정 금지 경계

아우라딘은 다른 팀원이 소유한 기존 기능이므로 다음 영역은 새 기능 구현 범위에서 제외한다.

- `apps/mobile/src/features/recommendation/screens/AuradinSearchScreen.tsx`
- `apps/mobile/src/features/recommendation/screens/views/`
- `apps/mobile/src/features/recommendation/components/ds/`
- `apps/mobile/src/features/recommendation/services/auradinSearchService.ts`
- 아우라딘이 사용하는 mock, suggestion, attachment 및 타입 계약
- `services/backend/app/api/search_sessions.py`
- `services/backend/app/services/auradin_agent/`
- `services/backend/app/services/auradin_catalog/`
- `data/auradin/` 및 아우라딘 세션 스키마와 설정

기존 코드의 아이디어나 외부 동작을 참고할 수는 있지만 파일을 수정하거나 내부 함수를 import해 결합하지 않는다. 새 기능 때문에 기존 아우라딘 테스트의 기대값을 변경하지도 않는다.

아우라딘은 완성 룩과 부위별 방법이 아니라 개별 제품 검색에 최적화되어 있으므로 새 기능의 기본 추천 엔진으로 사용하지 않는다. 새 기능은 독립적으로 동작하며 아우라딘이 변경되거나 사용할 수 없어도 사용자 경험이 유지되어야 한다.

비교가 필요할 때만 개발 및 QA 전용 `AuradinComparisonProvider`가 공개 API를 black-box로 호출할 수 있다. 이 provider는 feature flag 뒤에 두고 사용자용 결과를 결정하지 않는다. 비교 결과는 같은 입력에 대한 관련성, 룩 전체 조화, 구매 가능성, 지연 시간, 추가 질문 수를 평가하는 용도로만 사용한다. 아우라딘 내부 코드를 import하거나 수정하지 않는다.

### 6.3 백엔드 경계

현재 `/search/sessions`와 `auradin_agent`는 구매 가능한 화장품 후보 검색에 최적화되어 있다. 완성 룩, 부위별 방법, 세 가지 룩 역할을 동일한 제품 검색 상태에 억지로 추가하지 않는다.

메이크업 룩 추천은 별도 API, 서비스, 타입 및 저장소 계약을 사용한다. 구현 방식은 프로젝트의 일반적인 인증 및 DB 패턴을 따르되 아우라딘 파일을 수정하거나 내부 구현을 호출하지 않는다.

MVP 제품 provider는 새 기능이 소유하는 검수된 fixture와 룩 전체의 색상, 질감, 상황, 예산을 함께 고려하는 결정적 매칭 규칙을 사용한다. 제품 데이터에는 브랜드, 제품명, 색상, 부위, 추천 근거, 이미지 및 구매 링크를 담을 수 있다. 실제 상용 상품 검색으로 교체할 때도 `ProductRecommendationProvider` 계약 뒤에서 변경한다.

- 인증된 세션 소유권
- PostgreSQL 또는 메모리 세션 저장
- TTL과 취소
- 구조화된 질문과 답변
- 질문 수 제한
- 결과 생성 실패 시 결정적 fallback
- 독립 제품 provider와 대체 제품 매핑

권장 API 계약은 다음과 같다.

```text
GET  /api/makeup/scenarios
POST /api/makeup/recommendation-sessions
GET  /api/makeup/recommendation-sessions/{sessionId}
POST /api/makeup/recommendation-sessions/{sessionId}/answers
POST /api/makeup/recommendation-sessions/{sessionId}/cancel
POST /api/makeup/recommendation-sessions/{sessionId}/refine
```

세션 시작 요청은 `scenarioId` 또는 자유 `prompt`, 분석 정보 사용 여부와 사용 가능한 리포트 ID를 받는다. 질문 답변 요청은 선택지 또는 자유 답변 중 하나를 받고, 마지막 답변에는 `additionalConstraints`를 함께 받을 수 있다.

```json
{
  "questionId": "q-2-boldness",
  "optionId": "noticeably-different",
  "freeText": null,
  "additionalConstraints": "글리터 제외, 립 강조, 15분 이내"
}
```

### 6.4 전체 흐름

```text
시나리오 피드 로드
→ 시나리오 선택 또는 자유 입력
→ 프로필 사용 동의 상태와 함께 추천 세션 시작
→ 서버가 구조화된 의도와 기존 소프트 선호 병합
→ 정보가 부족하면 질문 반환
→ 모바일이 선택 또는 자유 답변 제출
→ 마지막 답변에는 펼쳐진 추가 조건을 함께 제출
→ 서버가 anchor, bold, discovery 룩 생성
→ 독립 제품 provider가 룩별 제품 세트를 연결
→ 모바일 결과 화면과 AR 진입 제공

개발 및 QA 비교가 켜진 경우에만:
→ 같은 조건을 AuradinComparisonProvider에 전달
→ 자체 결과와 아우라딘 결과를 비교 지표로 기록
```

## 7. 상태 및 실패 처리

첫 화면과 질문 및 결과 화면은 다음 상태를 모두 가진다.

- loading
- empty fallback
- error with retry
- refreshing
- session expired
- partial result

상세 동작은 다음과 같다.

- 시나리오 API 실패: 로컬 검수 문구를 즉시 노출한다.
- 개인화 실패: 개인화 이유를 숨기고 기본 문구 세트를 사용한다.
- 질문 생성 실패: 결정적 기본 질문을 사용하거나 현재 정보로 결과를 생성한다.
- 세션 만료: 기존 프롬프트와 답변을 유지한 채 새 세션으로 다시 시작할 수 있게 한다.
- 일부 룩 생성 실패: 성공한 결과를 먼저 보여주고 부족한 슬롯만 다시 시도한다.
- 대표 이미지 실패: 이미지 placeholder와 텍스트 추천을 유지한다.
- 제품 provider 실패: 룩 방법은 유지하고 검수된 fallback 제품 세트를 표시한다.
- refine 실패: 기존 결과를 유지하고 재시도 메시지만 표시한다.
- 사용자가 이탈: 세션 취소는 best-effort로 처리하고 화면 이탈을 막지 않는다.

## 8. 개인정보 및 안전

- 얼굴 분석과 취향 정보는 명시된 `내 분석 결과 반영` 체크 상태에서만 사용한다.
- 사용자가 분석 정보 사용을 끄면 해당 세션과 개인화 문구 생성에 전달하지 않는다.
- AI가 연애 상태, 직업, 경제력, 성격과 같은 민감하거나 사적인 특성을 사용자 데이터에서 추정해 문구를 생성하지 않는다.
- `전남친 결혼식`이나 캐릭터형 문구는 사용자가 선택할 수 있는 창작 시나리오이며 실제 사용자 상태로 저장하거나 단정하지 않는다.
- 제품 추천은 화장품 효능이나 외모 변화를 보장하지 않는다.
- 알레르기나 피부 회피 조건은 다른 미적 선호보다 우선한다.

## 9. 테스트 및 검증

### 9.1 모바일

- 시나리오 30~36개 노출과 첫 6개 말투 혼합
- 에디토리얼형, 장면형, 독백형, 서사형, 캐릭터형 카피 혼합과 젠더 뉴트럴 문구 검증
- 불필요한 `오늘` 및 동일 종결 반복 방지
- 12열 dense placement가 다양한 칩 크기로 빈 공간을 채우는지 검증
- 모든 시나리오 문구가 말줄임 없이 완전히 보이는지 검증
- 컨테이너 폭과 글꼴 배율 변경 시 재배치 및 전체 폭 fallback 검증
- 칩 팔레트와 폰트 크기 분산, 최소 터치 영역과 접근성 순서 검증
- 하단 플로팅 CTA의 safe area, 키보드 및 스크롤 겹침 검증
- 중복 의미 및 만료된 트렌드 문구 제외
- 분석 정보 사용 토글과 요청 컨텍스트
- 시나리오 선택 및 자유 입력 세션 시작
- 선택지 답변과 자유 답변 매핑
- 최대 3회 질문 제한 표시 및 상태 전환
- 마지막 질문에서만 `+ 조건 추가`와 명시적 `추천받기` 노출
- 추가 조건이 마지막 답변과 함께 한 번만 전송됨
- 세 가지 결과 역할 및 상세 매핑
- 결과 카드 상세의 기본 접힘, 펼치기 및 AR·저장 액션 유지
- loading, empty, error, retry, 만료 및 partial 상태
- 저장 및 AR 네비게이션 계약
- provider 교체와 QA 비교 flag가 사용자용 결과를 바꾸지 않는지 검증
- 모바일 typecheck

### 9.2 백엔드

- 세션 소유권과 TTL
- 시나리오 또는 자유 프롬프트 입력 검증
- 분석 정보가 하드 필터가 아닌 소프트 선호로 병합됨
- 이미 알려진 정보를 다시 질문하지 않음
- 보통 1~2회, 최대 3회 질문 제한
- 선택지와 자유 답변의 상호 배타적 검증
- 마지막 답변의 추가 조건 우선순위
- 조건 충돌 및 후보 부족 시 명시적 복구 응답
- anchor, bold, discovery 결과의 역할 및 다양성
- 부분 생성 및 enrichment 실패 fallback
- 독립 제품 provider와 대체 제품 매핑
- 동일 입력에 대한 선택적 아우라딘 비교 provider 격리
- 취소, 만료 및 refine 계약

### 9.3 제품 지표

MVP 비교 대상은 한 세션당 12개, 24개, 36개 문구다. 다음 지표로 노출량을 조정한다.

- 시나리오 선택률
- 첫 선택까지 걸린 시간
- 직접 입력 비율
- 스크롤 깊이
- `새로운 시나리오 보여줘` 사용률
- 질문 중단률과 질문 수
- 결과 저장률과 AR 진입률
- anchor, bold, discovery별 선택률

## 10. MVP 범위와 제외 범위

MVP에 포함한다.

- 자유 입력과 30~36개 시나리오 피드
- 모노톤과 일부 강조색, 3단계 폰트, 텍스트 비절단 퍼즐 칩 레이아웃
- 하단 고정 자유 입력 CTA와 작은 `내 분석 결과 반영` 체크 옵션
- 검수 문구 fallback과 새 세트 보기
- 분석 결과 사용 상태와 선택적 개인화
- 최대 3회의 적응형 질문
- 마지막 질문의 인라인 `+ 조건 추가`
- 세 가지 완성 룩, 방법, 제품 결과
- 독립 제품 provider와 검수된 MVP fixture
- 저장, refine 및 기존 AR 흐름 진입
- 개발 및 QA 전용 아우라딘 비교 provider 계약
- 모바일 및 백엔드 핵심 계약 테스트

MVP에서 제외한다.

- 추천 생성 전에 사용자 얼굴에 합성된 이미지를 필수 생성하는 기능
- 캘린더, 연락처 또는 위치의 자동 사용
- 검수되지 않은 실시간 밈을 무제한 노출하는 기능
- 첫 화면 진입을 막는 실시간 AI 문구 생성
- 사용자의 사적 관계나 경제적 배경 추정
- 아우라딘 모바일 또는 백엔드 코드 수정
- 아우라딘 내부 구현 import 또는 사용자용 런타임 의존

## 11. 완료 기준

- 사용자는 첫 화면에서 재미있는 문구를 탐색하거나 직접 원하는 메이크업을 입력할 수 있다.
- 시나리오 세트는 에디토리얼, 장면, 독백, 서사, 캐릭터형 카피가 균형 있게 섞이며 기본 문구는 젠더 뉴트럴하다.
- 시나리오 칩은 다양한 색, 크기와 폰트를 가지면서 빈 공간을 퍼즐처럼 채우고 어떤 문구도 잘리지 않는다.
- 질문 선택지는 전체 폭으로 명확하게 보이고 결과 상세는 필요할 때 펼칠 수 있다.
- AI는 기존 사용자 정보와 현재 프롬프트를 이용해 필요한 질문만 최대 3회 한다.
- 마지막 질문에서는 별도 턴 없이 조건을 추가할 수 있다.
- 결과는 서로 구별되는 세 가지 룩과 부위별 방법 및 조화로운 제품 세트를 독립적으로 제공한다.
- 실패하거나 오프라인이어도 첫 화면과 데모 흐름을 사용할 수 있다.
- 아우라딘은 개발 및 QA 비교에만 선택적으로 사용하며 기존 파일과 동작을 변경하지 않는다.
