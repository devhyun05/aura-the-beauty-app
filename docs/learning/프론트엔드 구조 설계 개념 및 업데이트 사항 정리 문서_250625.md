# 모바일 프론트엔드 구조 학습 문서

정리일: 2026-06-26

이 문서는 현재 `apps/mobile` 구조를 이해하기 위한 학습용 문서다. 과거 브랜치 비교나 리팩터링 히스토리는 다루지 않고, 지금 코드에서 실제로 쓰는 구조와 개념을 기준으로 설명한다.

현재 기획/작업 기준 문서:

- `docs/mobile/FRONTEND_WORK_GUIDE.md`
- `docs/planning/MOBILE_SCREEN_DETAIL_FEATURE_SPEC.md`
- `docs/planning/NAMING_DECISIONS.md`

## 1. 프로젝트 현재 범위

현재 모바일 앱은 React Native, Expo, TypeScript, React Navigation, Tamagui 기반의 프론트엔드 UI/UX 구현 단계다.

- 실제 백엔드 API는 붙이지 않는다.
- 실제 Unity AR, ARKit/ARCore, AI 모델은 붙이지 않는다.
- 화면은 실제 서비스 흐름처럼 구성하지만 데이터는 mock/service/type 계층으로 제공한다.
- 새 라이브러리는 팀 합의 없이 추가하지 않는다.

이 구조를 이해할 때 중요한 점은 "완성된 백엔드 앱"이 아니라 "나중에 API와 AR 모듈로 교체하기 쉬운 프론트엔드 데모 앱"이라는 것이다.

## 2. 폴더 구조를 보는 법

현재 핵심 구조:

```text
apps/mobile/src/
├─ app/
│  └─ navigation/
├─ assets/
├─ features/
│  ├─ ar/
│  ├─ auth/
│  ├─ face-analysis/
│  ├─ face-capture/
│  ├─ home/
│  ├─ makeup-feedback/
│  ├─ onboarding/
│  ├─ profile/
│  ├─ recommendation/
│  └─ reference-makeup-extraction/
└─ shared/
   ├─ mocks/
   ├─ services/
   ├─ theme/
   ├─ types/
   └─ ui/
```

`features`는 기능별 화면과 로직이 모이는 곳이다. 예를 들어 얼굴 분석은 `features/face-analysis`, 메이크업 피드백은 `features/makeup-feedback`, AR 필터는 `features/ar`에 둔다.

`shared`는 여러 기능에서 같이 쓰는 공통 계층이다. 공통이라고 해서 아무 파일이나 올리는 곳은 아니다. 여러 화면이 같은 계약으로 재사용할 때만 shared로 올리는 것이 좋다.

## 3. Feature-based architecture

Feature-based architecture는 기능별로 코드를 묶는 방식이다.

좋은 예:

```text
features/makeup-feedback/
├─ components/
├─ mocks/
├─ screens/
├─ services/
└─ types.ts
```

장점:

- 한 기능의 화면, mock, service, type을 같이 찾기 쉽다.
- 기획 변경이 들어왔을 때 수정 범위가 좁다.
- 팀원이 서로 다른 기능을 작업할 때 충돌이 줄어든다.

주의할 점:

- 여러 기능에서 진짜로 재사용할 때만 `shared`로 올린다.
- 한 기능에서만 쓰는 작은 컴포넌트는 feature 내부 `components`에 둔다.

## 4. Screen content와 screen chrome

화면 content는 사용자가 보는 실제 기능 UI다.

- 추천 제품 카드
- 얼굴 분석 보고서
- 메이크업 피드백 점수
- AR 필터 옵션 카드
- 프로필 수정 폼

화면 chrome은 content를 감싸는 공통 프레임이다.

- 상단 header
- 하단 footer
- 뒤로가기/닫기/공유 버튼
- status bar
- fullscreen 여부
- safe area padding

현재 앱은 route별 chrome 정책을 `routeChrome.ts`에 모은다. 덕분에 feature screen이 header/footer 결정을 반복하지 않아도 된다.

## 5. Navigation 구조

현재 앱은 React Navigation을 사용한다.

주요 파일:

- `apps/mobile/src/app/navigation/RootNavigator.tsx`
- `apps/mobile/src/app/navigation/MainTabNavigator.tsx`
- `apps/mobile/src/app/navigation/routeTypes.ts`
- `apps/mobile/src/app/navigation/routeChrome.ts`
- `apps/mobile/src/app/navigation/linkingConfig.ts`
- `apps/mobile/src/app/navigation/routes/`
- `apps/mobile/src/app/navigation/flowState.tsx`
- `apps/mobile/src/app/navigation/demoFlowState.ts`

각 파일의 역할:

| 파일 | 역할 |
| --- | --- |
| `RootNavigator.tsx` | root stack route를 등록한다. |
| `MainTabNavigator.tsx` | 홈, 추천, 마이페이지 탭을 관리한다. |
| `routeTypes.ts` | route 이름과 params 타입을 정의한다. |
| `routeChrome.ts` | route별 header/footer/fullscreen/status bar 정책을 정의한다. |
| `linkingConfig.ts` | deep link path를 관리한다. |
| `routes/*.tsx` | 플로우별 navigation callback과 기존 screen props를 연결한다. |
| `flowState.tsx` | route param으로 넘기기 어려운 임시 플로우 상태를 관리한다. |
| `demoFlowState.ts` | 화면 캡처나 데모용 seed 상태를 만든다. |

## 6. Route type

`routeTypes.ts`는 화면 이름과 화면에 필요한 parameter를 타입으로 고정한다.

예:

```ts
MakeupCorrectionTip: {pointId: string};
FaceAnalysisReportDetail: {reportId?: string} | undefined;
```

이렇게 하면 `navigation.navigate(...)`를 잘못 호출하는 실수를 TypeScript가 잡아줄 수 있다. 화면 이동은 런타임 오류가 나기 쉬운 영역이라 route type이 중요하다.

## 7. Route chrome

`routeChrome.ts`는 각 화면의 성격을 선언한다.

현재 depth:

| Depth | 의미 |
| --- | --- |
| `entry` | 로그인/온보딩 같은 앱 진입 화면 |
| `main` | 하단 footer가 있는 주요 탭 |
| `sub` | 상세, 목록, 폼, 진행 화면 |
| `immersive` | 카메라, AR, 추출 편집 화면 |
| `terminal` | 저장 완료 같은 플로우 종료 화면 |

현재 kind:

| Kind | 의미 |
| --- | --- |
| `mainTab` | main tab header/footer를 사용한다. |
| `detail` | route-level detail header를 사용한다. |
| `fullscreen` | 일반 header/footer 없이 화면 자체 UI를 사용한다. |

이 구조는 "이 화면에 footer가 보여야 하나?" 같은 질문을 코드 계약으로 만든다.

## 8. Navigation adapter

route adapter 파일은 React Navigation과 기존 screen props를 이어주는 중간 계층이다.

예:

```text
React Navigation route
-> routes/faceAnalysisRoutes.tsx
-> feature screen props
```

장점:

- feature screen을 크게 뜯지 않고 navigation 구조를 바꿀 수 있다.
- flow state 접근과 route 이동 로직을 screen 밖으로 뺄 수 있다.

현재 구조:

- `routes/authRoutes.tsx`: 로그인/온보딩 route adapter
- `routes/faceAnalysisRoutes.tsx`: 얼굴 촬영과 얼굴 분석 report route adapter
- `routes/arRoutes.tsx`: AR 필터, 형태 수정, 필터 편집 route adapter
- `routes/makeupFeedbackRoutes.tsx`: 피드백 촬영/결과/수정 가이드 route adapter
- `routes/referenceMakeupExtractionRoutes.tsx`: 레퍼런스 추출/저장/레시피 route adapter
- `routes/profileRoutes.tsx`: 마이페이지와 프로필 수정 route adapter
- `routes/recommendationRoutes.tsx`: 추천 제품과 저장/좋아요 목록 route adapter
- `routes/routeUtils.tsx`: route adapter가 공유하는 navigation helper와 main tab chrome wrapper

실무 팁:

- route adapter에는 "어느 화면으로 이동하는가"와 "flow state를 언제 저장하는가"만 둔다.
- feature screen에는 `navigation.navigate`를 직접 넣지 않고 `onPress...`, `onComplete...` 같은 props를 전달한다.
- route rename을 할 때는 `routeTypes.ts`, `routeChrome.ts`, `linkingConfig.ts`, `RootNavigator.tsx`, 관련 route adapter, 테스트를 한 세트로 바꾼다.

## 9. Flow state

모든 데이터를 route param으로 넘기면 안 된다.

route param에 적합한 값:

- `reportId`
- `pointId`
- 간단한 화면 진입 식별자

flow state에 적합한 값:

- 선택한 사진 객체
- 메이크업 피드백 결과
- 레퍼런스 메이크업 추출 결과
- 저장된 메이크업 룩 preview

현재 앱은 `NavigationFlowStateProvider`로 이런 임시 상태를 관리한다. 일반 앱 기본 상태는 clean state이고, 화면 캡처나 데모가 필요할 때만 `demoFlowState.ts`의 seed를 주입한다.

## 10. Mock, service, type 분리

현재 프로젝트는 mock 데이터를 사용하지만, 나중에 실제 API로 바꾸기 쉬워야 한다.

권장 흐름:

```text
screen
-> service
-> mock data
-> type
```

화면이 mock 파일을 직접 깊게 알면 API 전환 때 화면을 많이 고쳐야 한다. service를 거치면 mock을 API 호출로 바꿀 때 화면 변경을 줄일 수 있다.

예:

- `shared/services/faceAnalysisService.ts`
- `features/home/services/homeService.ts`
- `features/recommendation/services/productRecommendationService.ts`
- `features/makeup-feedback/services/makeupFeedbackService.ts`

## 11. Design tokens

반복되는 디자인 값은 `shared/theme`에서 관리한다.

주요 파일:

- `shared/theme/colors.ts`
- `shared/theme/spacing.ts`
- `shared/theme/radius.ts`
- `shared/theme/shadows.ts`
- `shared/theme/typography.ts`
- `shared/theme/iconSize.ts`

좋은 예:

```tsx
fontSize: typography.fontSize.md,
padding: spacing.lg,
fontWeight: typography.fontWeight.semibold,
```

피해야 할 예:

```tsx
fontSize: 17,
padding: 23,
fontWeight: '600',
```

토큰을 쓰면 화면 간 톤이 맞고, 디자인 방향이 바뀔 때 한곳에서 조정하기 쉽다.

## 12. 네이밍 기준

현재 앱은 다음 용어를 기준으로 한다.

| 개념 | 현재 용어 |
| --- | --- |
| 사용자-facing 메이크업 카드 | `룩` / `Look` |
| AR에 적용/저장 가능한 효과 전체 | `메이크업 필터` / `MakeupFilter` |
| 얼굴 전체 룩 | `TotalMakeupLook` |
| 특정 부위 룩 | `PointMakeupLook` |
| 메이크업 부위 기준 타입 | `MakeupArea` |
| AR 형태 옵션 | `Shape` |
| 사용자가 움직이는 형태점 | `shapePoint` |
| 얼굴 진단/분석 | `FaceAnalysis` |
| 현재 메이크업 평가 | `MakeupFeedback` |
| 레퍼런스 사진 추출 | `ReferenceMakeupExtraction` |
| 추천 제품 항목 | `RecommendedProduct` |

피해야 할 방향:

- 룩 의미로 `Style`을 새로 만들지 않는다.
- AR 형태 의미로 `Location`을 새로 만들지 않는다.
- 현재 얼굴 진단 기능명으로 `ImageAnalysis`를 쓰지 않는다.
- 사용자가 움직이는 형태점을 `landmarkPoint`라고 부르지 않는다.

자세한 결정 이유는 `docs/planning/NAMING_DECISIONS.md`를 따른다.

## 13. 이번 구조 정리에서 배울 것

이번 리팩터링은 기능을 새로 많이 늘리는 작업보다 "변경 범위를 작게 만드는 구조"를 만드는 작업에 가깝다.

핵심 적용:

- route adapter를 플로우별 파일로 나누어 화면 이동 충돌 범위를 줄였다.
- 저장 route는 `MakeupFilterSave`, 레시피 route는 `MakeupRecipeDetail`/`MakeupRecipeSaveComplete`로 최종화했다.
- `ProfileEditScreen`, `FaceAnalysisReportDetailScreen`, `MakeupCorrectionGuideOverlayScreen`, `FullscreenOverlay`에서 순수 모델 또는 공통 UI를 별도 파일로 분리했다.
- AR 형태 편집은 `shapePoint.offset`을 직접 drag로 바꾸고, 개별 reset/전체 reset/save preset 모델을 service에 모았다.
- `FaceAnalysisMakeupGuideline`, `makeupGuideline`처럼 `Guide`와 `Guideline`을 역할에 맞게 나눴다.

기초 개념:

- "route"는 앱에서 이동 가능한 화면의 이름이다.
- "adapter"는 navigation 라이브러리의 API와 우리 feature screen의 props를 연결하는 얇은 중간 계층이다.
- "service/model 함수"는 화면에서 직접 계산하지 않아도 되는 순수 계산이나 데이터 변환을 모은 함수다.
- "presentation component"는 데이터를 받아 UI만 그리는 컴포넌트다.

실무 팁:

- 큰 화면을 볼 때 바로 UI를 다 뜯지 말고, 먼저 순수 함수와 반복 UI부터 분리한다.
- 이름 변경은 검색 문자열 하나만 바꾸지 말고 route type, deep link, chrome, 테스트, 문서를 함께 바꾼다.
- drag 같은 인터랙션은 화면에서 좌표를 직접 계산하지 말고 service 함수로 "픽셀 이동량 -> 도메인 offset"을 변환한다.
- TODO 문서는 완료 후 남겨두면 다시 혼란의 출처가 되므로, 완료 상태가 코드/기획/학습 문서에 반영되면 제거한다.

## 14. 새 화면을 만들 때 체크할 것

1. 이 화면은 어떤 feature에 속하는가?
2. route가 필요한 화면인가, feature 내부 컴포넌트인가?
3. route라면 `routeTypes.ts`, `routeChrome.ts`, `linkingConfig.ts`가 필요한가?
4. header/footer/fullscreen 정책은 무엇인가?
5. 데이터는 mock/service/type 계층을 통하는가?
6. shared theme token을 쓰는가?
7. 새 이름이 `NAMING_DECISIONS.md` 기준과 충돌하지 않는가?
8. 화면 상태가 route param에 들어갈 값인지, flow state에 들어갈 값인지 구분했는가?

이 순서로 보면 새 화면을 추가할 때 구조가 흔들릴 가능성이 줄어든다.
