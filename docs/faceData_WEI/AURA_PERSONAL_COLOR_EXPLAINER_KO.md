# 퍼스널 컬러, 뭐가 뭔지 한눈에 정리

> 대상 독자: 팀 전원(비개발자 포함). "퍼스널 컬러는 쿨 라이트 서머라는데 톤 요약은 왜 쿨 라이트 뮤트 톤이지?" 같은 혼란을 풀기 위한 문서.
> 작성일: 2026-07-14 · 기준 코드: `apps/mobile/src/features/personal-color/services/personalColorCore/`, `services/backend/app/services/openai_analysis.py`

## 1. 가장 중요한 사실: 출처가 두 곳이다

보고서 화면에 보이는 값들은 **서로 다른 두 시스템**이 만든다.

| 화면에 보이는 것 | 예시 | 누가 만드나 | 성격 |
|---|---|---|---|
| 보고서 상단 "퍼스널 컬러" | 쿨 라이트 서머 | **백엔드 LLM** (사진 + 기기 실측값 참고) | 자유 서술 텍스트 |
| 보고서 상단 "톤 요약" | 쿨 라이트 뮤트 톤 | **백엔드 LLM** | 자유 서술 텍스트 (18자 이내 명사구) |
| 보고서 상단 "추천 무드" | 뮤트 로즈 데일리 룩 | **백엔드 LLM** | 자유 서술 텍스트 (18자 이내 무드명) |
| "퍼스널 컬러 진단" 카드 — 타입명(여름 라이트), 5축 막대, 측정 신뢰도, 판정 상태 칩 | 여름 라이트 · 신뢰도 72% | **온디바이스 엔진** (수학, LLM 아님) | 결정론적 계산 — 같은 입력이면 항상 같은 결과 |
| 카드의 색 계열 칩 "쿨 · 미드 · 클리어" 등 | 잘 어울리는 색 계열 | **온디바이스 엔진** (팔레트 모듈) | 결정론적 계산 |

- **온디바이스 엔진**: 아이폰에서 사진 픽셀을 직접 계산한다. LLM이 전혀 개입하지 않는다. 12톤 타입, 5축 값, 신뢰도, 색 계열 칩이 모두 여기서 나온다.
- **백엔드 LLM**: 사진을 보고 보고서 글(톤 요약, 추천 무드, 메이크업 가이드 등)을 쓴다. 설정에 따라 Bedrock Claude 또는 OpenAI 비전 모델이 쓰인다. 이때 **기기 실측 결과(`measuredPersonalColor`)를 함께 받아서**, 사진 관찰과 실측이 다르면 실측을 우선하라고 프롬프트되어 있다.

즉 **"쿨 라이트 서머"도, "쿨 라이트 뮤트 톤"도, "추천 무드"도 전부 LLM이 쓴 문장**이다. 다만 LLM이 아무렇게나 쓰는 게 아니라, 기기 엔진이 계산한 12톤 코드(예: `summer_light`)와 5축 수치를 근거 자료로 받아서 한국어로 풀어 쓴다. ("영문 톤 코드를 그대로 쓰지 말고 한국어로 풀어 써"라는 지시가 프롬프트에 있어서 `summer_light` → "쿨 라이트 서머"처럼 번역된다.)

## 2. 온디바이스 엔진: 색을 어떻게 계산하나 (6단계)

```
사진 촬영 (AE/AWB 잠금)
   ↓
① 부위별 픽셀 수집     볼 좌/우 + 이마(→피부), 머리카락, 입술, 흰자(조명 보정용)
   ↓
② 조명 보정            흰자 색으로 조명의 색 왜곡을 추정해 되돌림 (충혈이면 스킵)
   ↓
③ Lab 변환 + 5축 점수   각 축을 -1 ~ +1 점수로 환산
   ↓
④ 12톤 분류            내 5축 좌표에서 가장 가까운 타입 찾기 (확률로)
   ↓
⑤ 판정 상태            확정 / 걸침(혼합) / 참고 / 판정 불가
   ↓
⑥ 색 계열 팔레트       잘 어울리는 색 계열 칩 ("쿨 · 미드 · 클리어" 등)
```

### ① 부위별 픽셀 수집
얼굴 랜드마크로 부위를 찾고, 번들거리는 픽셀(반사광)·과노출·저노출 픽셀은 버린 뒤 부위별 평균 색(RGB)을 구한다. 피부는 3개 패치(볼 좌/우, 이마)를 신뢰도 가중으로 합친다.

### ② 조명 보정
눈 흰자는 원래 "거의 무채색"이라는 성질을 이용한다. 촬영된 흰자가 기준색(살짝 웜한 자연 흰자색)에서 벗어난 만큼이 "조명 때문에 생긴 왜곡"이라 보고 되돌린다(von Kries 방식). 단, 충혈이면 흰자의 빨간기가 조명 탓이 아니므로 **보정을 건너뛰고** 그 사실을 표기한다.

### ③ Lab 변환 + 5축 점수
RGB를 **Lab 색공간**(밝기 L\*, 빨강-초록 a\*, 노랑-파랑 b\*)으로 바꾸고, 부위별로 아래 지표를 뽑아 인구 평균 대비 상대 점수(-1 ~ +1)로 만든다.

| 축 | 화면 표기 | 계산 재료 (쉽게) | -1 쪽 | +1 쪽 |
|---|---|---|---|---|
| temperature | 쿨 ↔ 웜 | 노란기 − 빨간기 (b\* − a\*) | 쿨 | 웜 |
| value | 라이트 ↔ 딥 | 어두운 정도 (1 − L\*/100) | 라이트(밝음) | 딥(어두움) |
| chroma | 뮤트 ↔ 비비드 | 색의 진하기 (채도 C\*) | 뮤트(탁함) | 비비드(선명) |
| clarity | 소프트 ↔ 클리어 | 채도·대비 기반 맑기 | 소프트 | 클리어 |
| contrast | 저대비 ↔ 고대비 | 피부↔머리, 피부↔입술의 밝기·색 차이 | 저대비 | 고대비 |

중요한 전제: 카메라 자동보정(AWB)을 잠근 뒤 찍기 때문에 절대적인 색 측정이 아니라 **"한 장면 안에서의 상대 측정"**이다. 카드 하단의 "절대 색이 아닌 한 장면 내 상대 측정 기준" 문구가 이것.

또한 clarity·contrast는 chroma·value와 정보가 많이 겹친다는 게 검증에서 확인되어 **분류에서 낮은 가중치**(0.4, 0.45)만 갖는다. 사실상 temperature와 value가 판정을 주도한다.

### ④ 12톤 분류
한국식 12톤(4계절 × 3세부)을 쓴다. 각 타입마다 "표준 좌표"(5축 프로토타입)가 정해져 있고, **내 측정 좌표에서 가장 가까운 타입**이 결과가 된다. 거리를 softmax로 확률로 바꿔서:

- `top` = 1등 타입 (예: `summer_light` → "여름 라이트")
- `secondary` = 2등 타입 (1·2등 확률 차가 작으면 "걸친 톤"으로 표시)
- `typeScore` = 1등의 확률

**12개 타입 전체:**

| 계절 | 타입 (표시명) |
|---|---|
| 봄 (웜) | 봄 라이트 · 봄 브라이트 · 봄 웜(트루) |
| 여름 (쿨) | 여름 라이트 · 여름 쿨(트루) · 여름 뮤트 |
| 가을 (웜) | 가을 뮤트 · 가을 웜(트루) · 가을 딥 |
| 겨울 (쿨) | 겨울 브라이트 · 겨울 쿨(트루) · 겨울 딥 |

참고로 "여름 라이트"의 표준 좌표는 `[온도 -0.5, 명도 -0.7, 채도 -0.25, 맑기 -0.25, 대비 -0.55]` — **쿨하고, 밝고, 채도는 살짝 낮은(=살짝 뮤트한) 쪽**이다. 이게 뒤에 나올 혼란의 열쇠다.

### ⑤ 판정 상태 (카드 오른쪽 위 칩)

| 칩 | 의미 |
|---|---|
| 확정 | 신뢰도 높음 + 1등 확률 충분 + 기기 캘리브레이션 적용됨 |
| 걸침(혼합) | 1등과 2등 확률 차이가 작아 두 톤에 걸쳐 있음 |
| 참고(보정 전) | 결과는 나왔지만 캘리브레이션 전이라 조명 따라 달라질 수 있음 |
| 판정 불가 | 측정 신호가 부족함 (축 4개 미만 또는 신뢰도 미달) |

### ⑥ 색 계열 팔레트 — "쿨 · 미드 · 클리어"의 정체
**12톤 타입과는 별개의 분류다.** 색(제품·의상 색)을 3가지 축으로 27칸에 나눈 좌표계:

- 언더톤: 웜 / 뉴트럴 / 쿨
- 명도: 라이트 / 미드 / 딥
- 채도: 뮤트 / 클리어 / 비비드

측정된 축값을 문턱값으로 밴딩해 "내 중심 칸"을 정한다. 예: 온도가 -0.25보다 쿨하면 `쿨`, 명도가 -0.33 ~ +0.33 사이면 `미드`, 채도·맑기가 **둘 다 -0.2보다 낮아야** `뮤트`(아니면 `클리어`).

그다음 중심 칸 **+ 인접 밴드**(옆 명도, 옆 채도 등)까지 넓혀 "잘 어울리는 색 계열" 칩 최대 4개를 보여준다. 각 칸에는 대표색 예시가 있다:

| 칸 (labelKo) | 대표색 |
|---|---|
| 쿨 · 라이트 · 뮤트 | 라벤더, 로즈, 더스티핑크 |
| 쿨 · 미드 · 클리어 | 블루, 푸시아, 민트 |
| 쿨 · 딥 · 비비드 | 버건디, 네이비, 마젠타 |
| 웜 · 라이트 · 클리어 | 살구, 피치, 코랄 |
| … | (총 27칸, `palette.ts`의 EXEMPLARS) |

"포인트로 쓰면 좋은 색 계열"(worst)은 반대 언더톤 × 반대 채도 쪽 칸이다. "안 어울림"이라고 단정하지 않고 얼굴에서 먼 곳(하의·가방)에 쓰라고 소프트하게 안내한다.

## 3. 그래서, 질문들에 대한 답

### Q1. "톤 요약"은 LLM이 하는 건가, 우리 엔진이 하는 건가?
**LLM이다.** 백엔드 `openai_analysis.py`가 사진과 기기 실측값을 LLM에 주고 `toneSummary`를 "18자 이내 짧은 명사구"로 쓰게 한다. 앱은 그 문자열을 그대로 표시할 뿐이다(`faceAnalysisReportDetailModel.ts`의 `{label: '톤 요약', value: report.toneSummary}`).

### Q2. "추천 무드"는?
**역시 LLM이다.** 같은 프롬프트에서 `recommendedMood`를 "18자 이내 짧은 무드명"으로 쓰게 한다. 이 무드는 이후 추천 메이크업 카드 1개의 콘셉트 근거로도 쓰인다.

### Q3. 퍼스널 컬러는 "쿨 라이트 서머"인데 톤 요약은 왜 "쿨 라이트 뮤트 톤"인가?
모순이 아니라 **같은 측정 결과를 두 가지 말로 표현한 것**이다.

1. 기기 엔진이 `summer_light`(여름 라이트)로 분류 → LLM이 이를 "쿨 라이트 서머"로 풀어 씀.
2. 여름 라이트의 표준 좌표 자체가 **채도가 살짝 낮은(뮤트 방향) 톤**이다. LLM이 실측 축값(채도 음수)을 보고 "뮤트 톤"이라는 단어로 요약한 것.
3. 헷갈리는 진짜 이유: 12톤 중에 "여름 **뮤트**"라는 타입명이 따로 있어서, "뮤트 톤"이라는 서술어가 타입명처럼 읽힌다. 하지만 톤 요약의 "뮤트"는 타입명이 아니라 **"채도가 낮다"는 형용사**다.

단, 톤 요약은 자유 서술이라 엔진의 고정 어휘와 1:1 대응이 보장되지 않는다. 이 어긋남이 계속 거슬리면 톤 요약 문구를 엔진 축값에서 결정론적으로 생성하도록 바꾸는 선택지도 있다(4절 참고).

### Q4. "쿨 미드 클리어"는 또 뭔가?
**12톤 타입이 아니라 색 계열 칩이다**(2-⑥절). "언더톤 쿨 × 명도 중간 × 채도 클리어"인 색 묶음(블루, 푸시아, 민트 계열)이 잘 받는다는 뜻이다.

"나는 라이트인데 왜 미드가 나오지?"가 되는 이유는 둘 중 하나:
- 팔레트 밴딩은 **분류된 타입이 아니라 측정 축값을 직접** 문턱값으로 자른다. 명도가 -0.33 문턱을 못 넘으면(충분히 밝지 않으면) `미드` 밴드가 된다. 타입 분류(가장 가까운 프로토타입 찾기)와 밴딩(문턱값 자르기)은 기준이 달라 경계 근처에서 어긋날 수 있다.
- 또는 중심 칸은 `쿨 · 라이트 · 클리어`인데, **인접 명도 밴드까지 넓혀 보여주는 로직** 때문에 `쿨 · 미드 · 클리어`가 함께 뜬 것.

같은 원리로 "톤 요약은 뮤트라는데 칩은 클리어네?"도 설명된다: 엔진 밴딩은 채도·맑기가 **둘 다 -0.2 미만**이어야 뮤트로 자르는데, 살짝만 음수면(예: -0.1) 칩은 `클리어`가 되고, LLM은 같은 값을 보고 "뮤트"라고 서술할 수 있다. 문턱값의 차이다.

## 4. 데이터 흐름 요약 + 파일 지도

```
[아이폰]                                        [백엔드]
사진 촬영
  → AURAPersonalColorAnalyzer.m (픽셀 수집)
  → personalColorCore/ (JS 엔진)
      colorMath.ts        RGB→Lab 변환
      axisModel.ts        5축 계산
      toneClassifier.ts   12톤 분류 (softmax)
      palette.ts          27칸 색 계열 팔레트
      engine.ts           오케스트레이터 + 판정 상태
  → 결과 A: PersonalColorTypeCard에 즉시 표시 ─────────┐
  → 결과 B: measuredPersonalColor 요약을 업로드 ────→ openai_analysis.py
       (faceAnalysisMeasurements.ts)                LLM이 사진+실측으로 보고서 작성
                                                     personalColor / toneSummary /
                                                     recommendedMood / 메이크업 가이드
                                                        ↓
[앱 보고서 화면]  ← faceAnalysisReportDetailModel.ts가 두 결과를 한 화면에 배치
```

| 알고 싶은 것 | 파일 |
|---|---|
| 5축·12톤 상수, 타입 한국어명, 프로토타입 좌표 | `personal-color/services/personalColorCore/constants.ts` |
| 12톤 분류 로직 | `personalColorCore/toneClassifier.ts` |
| 색 계열 27칸·대표색·best/worst 칩 | `personalColorCore/palette.ts` |
| 전체 파이프라인·판정 상태 | `personalColorCore/engine.ts` |
| 진단 카드 UI (축 막대, 칩) | `personal-color/components/PersonalColorTypeCard.tsx` |
| LLM 프롬프트 (톤 요약·추천 무드 생성 규칙) | `services/backend/app/services/openai_analysis.py` |
| 기기 실측 → LLM 전달 페이로드 | `face-analysis/services/faceAnalysisMeasurements.ts` |
| 보고서 요약 4줄 배치 | `face-analysis/services/faceAnalysisReportDetailModel.ts` |

### 손볼 만한 지점 (제안)
1. **용어 충돌**: 톤 요약의 "뮤트"(형용사)와 타입명 "여름 뮤트"가 같은 단어라 사용자 혼란이 구조적이다. LLM 프롬프트에 "12톤 타입명과 겹치는 단어(뮤트/브라이트/딥/라이트)는 톤 요약에 쓰지 마" 한 줄을 추가하거나, 톤 요약을 LLM 대신 엔진 축값에서 템플릿으로 생성하는 방법이 있다.
2. **칩 라벨**: "쿨 · 미드 · 클리어"가 타입명처럼 읽히므로 칩에 "색 계열" 같은 접두/설명을 붙이면 오해가 줄어든다.
