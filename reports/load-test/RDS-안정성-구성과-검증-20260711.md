# RDS 안정성 구성과 검증 - 2026-07-11

## 문서 목적

초기 등록 사용자 200명 기준으로 개발 RDS가 현재 부하를 감당할 수 있는지 확인하고, 데이터 손실과 장애 원인 미확인 위험을 줄이기 위해 실제 적용한 설정을 기록한다.

이번 단계의 목적은 DB 속도를 무조건 높이는 것이 아니다.

- 실수로 데이터를 삭제했을 때 복구할 수 있는 기간 확보
- RDS 인스턴스 자체가 실수로 삭제되는 것 방지
- 느린 쿼리와 DB 부하 원인 확인
- CPU, 메모리, 저장공간, 연결 수, deadlock 이상 조기 알림
- 대기 중인 운영체제 보안 업데이트를 예측 가능한 시간에 적용

## 적용 전 판단

최근 7일 지표와 PostgreSQL 내부 상태를 읽기 전용으로 점검했다.

현재 RDS의 CPU, 연결 수, 저장공간과 지연 시간은 안정적이다. 따라서 다음 항목은 적용하지 않았다.

- 인스턴스 사양 상향
- Multi-AZ 전환
- RDS Proxy 추가
- 근거 없는 인덱스 일괄 추가 또는 삭제
- 사용자 테이블 데이터 변경
- RDS 네트워크 공개 범위 변경

```powershell

```

스냅샷 생성과 OS 업데이트 예약은 반복 실행 시 뜻하지 않게 다시 수행되지 않도록 명시적인 스위치로 분리했다.

```powershell
.\scripts\aws\configure_rds_stability.ps1 `
  -CreatePreChangeSnapshot `
  -SchedulePendingOsUpdate
```

## 자동 백업 7일의 기능적 의미

사용자 데이터가 금요일에 잘못 삭제됐는데 월요일에 문제를 발견해도, 최근 7일 안의 시점으로 새 RDS를 복원해 데이터를 확인할 수 있다.

백업은 매일 20GiB 전체를 별도 복사하는 방식이 아니라 변경된 블록을 증분 저장한다. 자동 백업은 7일이 지나면 순환 삭제된다.

## 삭제 보호의 범위

삭제 보호는 AWS 콘솔이나 CLI에서 RDS 인스턴스 자체를 실수로 삭제하는 것을 막는다.

다음 작업까지 막아주는 기능은 아니다.

- 애플리케이션 SQL의 `DELETE`
- 잘못된 migration
- 사용자 데이터 값 덮어쓰기

이런 데이터 변경 사고는 7일 자동 백업과 수동 스냅샷으로 복구한다.

## 쿼리 성능 관측

`pg_stat_statements`는 모든 사용자 데이터나 SQL 실행 로그를 무한히 저장하지 않는다. 비슷한 SQL을 한 항목으로 묶어 다음 통계를 집계한다.

- 호출 횟수
- 총 실행 시간
- 평균 실행 시간
- 읽고 쓴 블록 수

설치는 사용자 테이블을 수정하지 않는 일회성 ECS 작업으로 실행했다.

| 항목 | 결과 |
|---|---|
| ECS task definition | `aura-postgres-observability-setup:1` |
| ECS task 종료 코드 | 0 |
| 확장 버전 | 1.11 |
| `shared_preload_libraries` | `pg_stat_statements` 포함 |
| `track_io_timing` | `on` |
| 설치 직후 집계 항목 | 1,644개 |

집계 항목 1,644개는 사용자 레코드 수가 아니라 DB가 구분한 쿼리 유형 수다.

일회성 작업 재현 스크립트:

```powershell
.\scripts\aws\run_postgres_observability_setup.ps1 -ImageUri <backend-image-uri>
```

## RDS 알람

기존 `aura-ops-alerts-dev` SNS 주제와 확인된 이메일 구독을 사용한다.

| 알람 | 조건 | 평가 | 적용 직후 상태 |
|---|---:|---:|---:|
| `aura-rds-cpu-high` | CPU 70% 이상 | 5분 지표 3개 중 2개 | OK |
| `aura-rds-free-memory-low` | 남은 메모리 100MiB 이하 | 5분 연속 2회 | OK |
| `aura-rds-free-storage-low` | 남은 저장공간 5GiB 이하 | 5분 연속 2회 | OK |
| `aura-rds-connections-high` | 연결 60개 이상 | 5분 연속 2회 | OK |
| `aura-rds-deadlock-detected` | deadlock 1건 이상 | 5분 합계 | OK |

연결 알람 60개는 현재 최대 설정 79개의 약 76%다. 문제가 생기기 전에 원인을 확인할 여유를 두기 위한 값이다.

## 운영체제 업데이트 예약

RDS에 대기 중이던 `system-update`를 다음 유지보수 창으로 예약했다.

```text
적용 예정: 2026-07-15 23:55 KST
유지보수 창: 수요일 23:55 ~ 목요일 00:25 KST
```

현재 RDS는 Single-AZ이므로 업데이트 중 짧은 DB 연결 중단이 발생할 수 있다. 앱에서 분석이나 저장 작업이 적은 시간에 진행되는지 확인하고, 다음 날 API와 DB 상태를 다시 확인한다.

## 비용 영향

현재 규모에서 이번 변경의 월 추가 비용은 `$0`에 가깝지만 다음 조건에서는 비용이 생길 수 있다.

- 자동 백업과 수동 스냅샷의 합계가 실행 중인 RDS의 무료 백업 할당량 20GiB를 초과
- 수동 스냅샷을 장기간 계속 쌓음
- Performance Insights 보존 기간을 기본 7일보다 길게 구매
- 계정 전체 CloudWatch 표준 알람 무료 제공량을 초과

현재 DB는 약 15.9MB이고 변경량도 작다. 자동 백업은 증분 방식이며 7일 후 순환된다. 이번 수동 스냅샷은 자동 삭제되지 않으므로 안정화 확인 후 불필요하면 삭제한다.

`pg_stat_statements`와 OS 업데이트에는 별도 AWS 사용료가 없다. 새 표준 알람 5개는 계정 전체 무료 범위 사용량에 따라 최대 월 수십 센트 정도의 소액이 발생할 수 있다.

## 최종 결정

초기 등록 사용자 200명 기준으로 현재 `db.t4g.micro` Single-AZ 인스턴스를 유지한다.

지금은 RDS 사양보다 복구 가능성과 문제 관측 능력을 먼저 보강하는 것이 비용 대비 적절하다. 실제 운영에서 CPU, 메모리, 연결 수 알람이 반복되거나 느린 쿼리가 확인되면 `pg_stat_statements` 근거를 바탕으로 쿼리, 인덱스, 인스턴스 사양을 순서대로 조정한다.

다음 서버 안정화 단계는 외부 API 비밀값을 Secrets Manager에 정리하고 ECS와 Lambda가 필요한 값만 IAM 권한으로 읽게 만드는 것이다.
