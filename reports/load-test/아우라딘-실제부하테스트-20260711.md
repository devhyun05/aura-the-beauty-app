# 아우라딘 실제 부하 테스트 - 2026-07-11

## 테스트 목적

실제 Naver 쇼핑 API와 Bedrock을 사용하는 아우라딘 추천 여정이 동시에 실행될 때 다음 항목을 확인했다.

- 사용자가 최종 추천 결과까지 정상적으로 도달하는지
- 일반 API 요청이 느려지거나 실패하지 않는지
- FastAPI ECS CPU와 메모리가 안정적인지
- RDS CPU와 연결 수가 안정적인지
- Bedrock 또는 Naver 타임아웃이 발생하는지
- 초기 등록 사용자 200명 단계에서 아우라딘 전용 워커가 필요한지

## 테스트 환경

- AWS 리전: `ap-northeast-2`
- API 경로: API Gateway -> 내부 ALB -> FastAPI ECS 태스크 1개
- API 태스크 크기: 0.5 vCPU, 메모리 1GB
- 데이터베이스: RDS PostgreSQL `db.t4g.micro`
- 아우라딘 세션 저장소: Postgres
- 대표 입력: 쿨톤, 글로시 핑크 립, 2만원 이하 조건
- 일반 API 측정 경로: `GET /api/analysis/reports`
- 일반 API 부하: 총 1,000건, 동시 요청 20개, 요청 간격 100ms

## 사용자 여정

한 번의 실제 여정은 다음 순서로 실행했다.

1. 추천 세션 생성
2. 현재 질문 조회
3. 질문의 유효한 선택지 자동 선택
4. 최대 3개의 질문에 답변
5. Naver 상품 보강과 Bedrock 추천 문구 생성
6. 최종 추천 결과 확인
7. 테스트 세션 취소 처리

## 사용자 체감 해석

동시 5명 결과의 전체 20.3초는 사용자가 한 화면에서 결과만 기다리는 시간이 아니다. 테스트 도구가 사람보다 빠르게 질문 3개에 연속으로 답하고 최종 결과까지 진행한 전체 시간이다.

실제 화면에서는 다음처럼 보인다.

- 추천 시작 후 첫 질문 표시까지 약 3~5초
- 각 질문 답변 후 다음 질문 또는 결과까지 보통 약 4초
- 가장 느린 답변 요청은 약 7.7초

현재 모바일 API 제한시간은 60초이므로 기술적인 타임아웃 여유도 있다.

## 최종 판정

초기 등록 사용자 200명 단계에서는 아우라딘을 FastAPI에 유지한다.

이유:

- 실제 동시 5명 전원이 최종 결과까지 성공했다.
- 일반 API 1,000건이 모두 성공했다.
- 일반 API p95가 500ms 기준보다 충분히 낮은 231ms였다.
- API CPU 최대가 70% 기준보다 낮은 58.4%였다.
- RDS 사용량이 매우 낮고 연결 수도 안정적이었다.
- Bedrock과 Naver 오류 또는 타임아웃이 없었다.

현재 아우라딘 전용 SQS와 ECS 워커를 추가하면 구조와 비용만 늘고, 초기 200명 기준으로 얻는 효과는 작다.
