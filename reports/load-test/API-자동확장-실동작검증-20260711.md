# API 자동 확장 실동작 검증 - 2026-07-11

## 문서 목적

FastAPI ECS 서비스가 요청 증가 시 자동으로 태스크를 늘리고, 부하가 끝나면 다시 줄이는지 AWS에서 직접 검증한 결과를 기록한다.

초기 등록 사용자 200명 기준에서 평소 비용은 현재와 동일하게 유지하면서, 몇 분 이상 계속되는 요청 증가에 대비하는 것이 목적이다.

## 자동 확장이 필요한 이유

기존 API 서비스는 `0.5 vCPU`, 메모리 `1GB` 태스크 1개로 고정돼 있었다. 요청이 몰려도 ECS가 자동으로 두 번째 API를 시작하지 않는 상태였다.

자동 확장을 사용하면 다음과 같이 동작한다.

```text
평상시
  -> FastAPI 태스크 1개

CPU 또는 요청 수가 일정 시간 기준 초과
  -> FastAPI 태스크 2개
  -> ALB가 두 태스크에 요청 분산

부하 종료 후 저부하 상태 유지
  -> FastAPI 태스크 1개로 축소
```

얼굴진단 ECS Worker의 확장과는 별개다. 이번 설정은 로그인, 조회, 아우라딘, 작업 생성과 상태 조회 등을 받는 FastAPI 서비스만 확장한다.

## 적용 설정

| 항목 | 값 |
|---|---:|
| 최소 API 태스크 | 1개 |
| 최대 API 태스크 | 2개 |
| CPU 목표값 | 60% |
| 내부 ALB 요청 목표값 | 태스크당 분당 1,000건 |
| 확장 cooldown | 60초 |
| 축소 cooldown | 600초 |
| API 태스크 크기 | 0.5 vCPU, 메모리 1GB |

적용된 정책:

- `aura-backend-api-cpu-target`
- `aura-backend-api-requests-target`

재현 가능한 배포 스크립트:

```powershell
.\scripts\aws\configure_api_autoscaling.ps1
```

스크립트는 ECS 서비스에 연결된 내부 ALB와 타깃 그룹을 직접 조회해 요청 수 정책의 `ResourceLabel`을 만든다. 같은 설정으로 다시 실행하면 기존 정책을 갱신하므로 반복 배포가 가능하다.

## CPU와 요청 수를 함께 보는 이유

일반 계산 작업은 CPU가 높아지므로 CPU 목표값으로 감지할 수 있다.

하지만 아우라딘은 Naver와 Bedrock 응답을 기다리는 시간이 있다. 이때 CPU는 낮아도 API 요청 연결은 오래 유지될 수 있다. 따라서 다음 두 조건 중 하나라도 발생하면 확장할 수 있도록 정책을 분리했다.

- 서비스 평균 CPU가 60%를 지속적으로 초과
- 내부 ALB의 태스크당 요청 수가 분당 1,000건을 지속적으로 초과

확장은 어느 한 정책이라도 필요하다고 판단하면 실행된다. 축소는 두 정책 모두 저부하라고 판단해야 실행된다.

## 적용 전 실측 상태

최근 7일 지표:

| 항목 | 결과 |
|---|---:|
| API CPU 평균 | 2.47% |
| API CPU p95 | 2.88% |
| API 메모리 최대 | 16.99% |
| 수정된 API 태스크 정의 50 등록 이후 5xx | 0건 |

평소에는 API 태스크 1개로 충분했다. 따라서 최소 용량을 2개로 올리지 않고 `최소 1, 최대 2`를 선택했다.

## 비용 계산

2026-07-11 AWS Pricing API의 서울 리전 Linux Fargate 단가:

- vCPU: 시간당 `$0.04656`
- 메모리: GB당 시간당 `$0.00511`

현재 API 태스크 1개의 시간당 비용:

```text
0.5 vCPU x $0.04656 + 1GB x $0.00511
= 시간당 $0.02839
```

730시간 기준 한 달 비용은 약 `$20.72`다.

| 두 번째 태스크 실행 시간 | 추가 월 비용 | API ECS 총 월 비용 |
|---|---:|---:|
| 실행되지 않음 | $0.00 | 약 $20.72 |
| 하루 1시간 | 약 $0.85 | 약 $21.57 |
| 하루 2시간 | 약 $1.70 | 약 $22.42 |
| 하루 6시간 | 약 $5.11 | 약 $25.83 |
| 한 달 내내 실행 | 약 $20.72 | 약 $41.45 |

이번 검증에서 두 번째 태스크는 약 16분 실행됐다. 추가 Fargate 비용은 약 `$0.008`로 1센트 미만이다.

이 계산은 API ECS 태스크의 증분 비용이다. 기존 ALB, RDS, API Gateway 비용은 포함하지 않는다.

## 부하 테스트 방법

유료 AI 호출을 발생시키지 않는 공개 상태 확인 경로를 사용했다.

```text
GET /health
```

이 경로는 FastAPI와 DB 연결 상태만 확인하며 OpenAI, Bedrock, Naver를 호출하지 않는다.

기준 테스트:

| 항목 | 결과 |
|---|---:|
| 요청 | 200건 |
| 동시 요청 | 2개 |
| 성공 | 200건 |
| 실패 | 0건 |
| 초당 요청 | 40.34건 |
| p95 | 67.39ms |

자동 확장 테스트:

| 항목 | 결과 |
|---|---:|
| 요청 | 12,000건 |
| 동시 요청 | 2개 |
| 성공 | 12,000건 |
| 실패 | 0건 |
| 실행 시간 | 248.12초 |
| 초당 요청 | 48.36건 |
| 평균 응답시간 | 41.34ms |
| p50 | 40.02ms |
| p95 | 52.44ms |
| p99 | 81.98ms |
| 최대 응답시간 | 272.34ms |
| API Gateway 5xx | 0건 |

부하 구간 ECS 자원 사용량:

| 항목 | 평균 | 최대 |
|---|---:|---:|
| API CPU | 7.24% | 30.45% |
| API 메모리 | 8.52% | 8.79% |

CPU는 60%를 넘지 않았다. 이번 확장은 요청 수 정책이 작동한 결과다.

## 1개에서 2개로 확장 결과

요청 수 정책에 입력된 1분 지표:

```text
02:37  2,981건
02:38  2,835건
02:39  2,914건
```

분당 1,000건 초과가 3번 연속 확인되자 요청 수 고부하 알람이 전환됐다.

| 시각 | 동작 |
|---|---|
| 02:42:44 | 요청 수 고부하 알람 전환, desired count 2 요청 |
| 02:43:00 | 두 번째 ECS 태스크 시작 |
| 02:43:37 | 두 ALB 타깃 그룹에 새 태스크 등록 |
| 02:44:19 | 확장 scaling activity 성공 |
| 02:44:42 | ECS 서비스 steady state |

확장 후 상태:

```text
desired=2
running=2
pending=0
내부 ALB healthy=2
외부 ALB healthy=2
API status=ok
database=connected
```

## 2개에서 1개로 축소 결과

부하 종료 후 `02:41~02:55`의 요청 수가 15분 연속 축소 기준인 분당 900건보다 낮았다.

| 시각 | 동작 |
|---|---|
| 02:58:30 | 요청 수 저부하 알람 전환, desired count 1 요청 |
| 02:58:41 | 두 번째 ECS 태스크 중지 |
| 02:58:51 | ECS 서비스 steady state |
| 02:59:04 | 축소 scaling activity 성공 |

축소 후 상태:

```text
desired=1
running=1
pending=0
내부 ALB healthy=1
외부 ALB healthy=1
API status=ok
database=connected
```

중지된 태스크는 기존 연결 보호를 위해 잠시 ALB에서 `draining` 상태를 거친 뒤 두 타깃 그룹에서 정상 제거됐다.

## 기능적으로 확인된 것

1. 평소에는 API 태스크 1개만 실행된다.
2. 요청 증가가 3분 이상 지속되면 두 번째 API 태스크가 자동으로 시작된다.
3. 확장 중에도 12,000건 요청이 모두 성공했다.
4. 두 API 태스크가 내부·외부 ALB 모두에서 정상 상태가 됐다.
5. 부하 종료 후 자동으로 태스크 1개로 돌아왔다.
6. 전체 확장·축소 구간에 API Gateway 5xx가 없었다.

## 반드시 알아야 할 한계

자동 확장은 첫 번째 순간 부하를 즉시 없애지 않는다.

- 고부하 지표가 3분 연속 필요하다.
- CloudWatch 지표와 알람 평가에 추가 지연이 있다.
- 새 ECS 태스크 시작과 ALB 상태 확인에도 시간이 필요하다.

이번 검증에서는 요청 증가 시작부터 두 번째 태스크의 steady state까지 수분이 걸렸다. 그동안 기존 API 태스크 1개가 요청을 처리한다.

항상 두 태스크가 준비된 무중단 여유 용량이 필요하다면 최소 용량을 2로 올려야 한다. 그러면 트래픽이 없어도 매월 약 `$20.72`가 추가된다. 초기 등록 사용자 200명 단계에서는 비용 대비 필요성이 낮아 최소 용량 1을 유지한다.

또한 Naver나 Bedrock 자체가 느린 상황은 API 태스크를 늘려도 외부 응답시간이 빨라지지 않는다. 자동 확장은 외부 제공자의 속도가 아니라 우리 FastAPI의 동시 요청 수용량과 부하 격리를 개선한다.

## 최종 결정

초기 등록 사용자 200명 기준 API 자동 확장을 다음 값으로 운영한다.

```text
최소 1
최대 2
CPU 목표 60%
태스크당 요청 목표 분당 1,000건
확장 cooldown 60초
축소 cooldown 600초
```

평소 비용은 API 태스크 1개 수준을 유지하고, 몇 분 이상 지속되는 부하에만 두 번째 태스크 비용을 지불한다.

다음 서버 안정화 단계는 RDS의 느린 쿼리, 인덱스, 백업과 복구 설정을 확인하는 것이다.
