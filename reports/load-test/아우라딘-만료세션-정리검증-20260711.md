# 아우라딘 만료 세션 자동 정리 검증 - 2026-07-11

## 문서 목적

아우라딘 대화 세션은 추천 과정에서만 필요한 임시 데이터다. 이 문서는 만료된 세션을 자동으로 정리하면서 사용자가 별도로 좋아요한 상품은 보존하는 구조와 AWS 실검증 결과를 기록한다.

## 기능적으로 무엇을 지우는가

정리 대상은 `auradin_search_sessions`에서 `expires_at < now()`인 행뿐이다.

세션에는 다음과 같은 임시 상태가 들어 있다.

- 사용자가 처음 입력한 추천 조건
- 아우라딘이 물어본 추가 질문
- 사용자가 선택한 답변
- 현재 추천 단계와 조건
- 해당 대화에서 만든 일회성 추천 결과 목록

세션이 만료되면 이 대화를 이어서 진행할 수 없고, 사용자는 새 추천 대화를 시작하게 된다.

## 무엇을 지우지 않는가

다음 데이터는 세션 정리와 별도 테이블에 있으므로 삭제하지 않는다.

| 데이터 | 저장 테이블 | 정리 여부 |
|---|---|---|
| 상품 원본 정보 | `products` | 유지 |
| 사용자가 좋아요한 상품 | `user_product_likes` | 유지 |
| 아직 만료되지 않은 아우라딘 세션 | `auradin_search_sessions` | 유지 |
| 만료된 아우라딘 대화와 임시 추천 결과 | `auradin_search_sessions` | 삭제 |

중요한 기준은 사용자가 상품의 하트를 눌렀는지다. 하트를 누른 상품은 대화 세션이 사라져도 좋아요 목록에 남는다. 대화 화면에 잠시 보였지만 좋아요하지 않은 추천 목록은 세션과 함께 정리된다.

## 실행 구조

```text
EventBridge: 30분마다 실행
  -> 일회성 ECS 정리 태스크 시작
     -> 2시간 넘게 processing인 AI 작업을 failed로 정리
     -> expires_at이 지난 아우라딘 세션 삭제
     -> 실행 종료
```

새 상시 서버나 새 스케줄은 추가하지 않았다. 기존 stuck job 정리용 30분 EventBridge 규칙과 일회성 ECS 태스크에 아우라딘 세션 정리를 함께 연결했다.

이 작업은 Lambda가 아니라 ECS 일회성 태스크에서 실행한다. 이미 DB 연결과 AI 작업 정리를 수행하던 유지보수 태스크를 재사용하면 별도 배포 단위를 늘리지 않고 같은 운영 경로에서 관리할 수 있기 때문이다.

## 구현 내용

- `services/backend/app/ops/cleanup_expired_auradin_sessions.py`
  - 만료 후보 조회
  - 만료 행 삭제
  - 세션 ID를 노출하지 않고 삭제 개수만 로그에 기록
- `services/backend/app/ops/cleanup_stuck_jobs.py`
  - 기존 AI stuck job 정리 후 아우라딘 만료 세션 정리 실행
  - `--dry-run`에서도 두 정리 대상을 모두 조회
- `services/backend/app/services/auradin_agent/session_manager.py`
  - `expires_at` 인덱스를 항상 보장
- `services/backend/app/db/init_db.py`
  - `schema.sql:auradin-sessions-v1` 마이그레이션 등록
- `scripts/aws/configure_stuck_job_cleanup_schedule.ps1`
  - 기존 30분 규칙이 통합 정리 태스크를 가리키도록 배포

삭제 SQL의 범위는 다음 조건으로 고정했다.

```sql
delete from auradin_search_sessions
where expires_at < now()
returning session_id;
```

`products`와 `user_product_likes`를 수정하는 SQL은 정리 코드에 없다.

## 코드 검증

| 검증 항목 | 결과 |
|---|---:|
| 정리·스키마 집중 테스트 | 21개 통과 |
| 백엔드 전체 테스트 | 401개 통과 |
| Git 공백·패치 검사 | 통과 |
| 배포 커밋 | `a8c0e44` |

테스트는 다음 동작을 고정한다.

- `expires_at < now()`인 세션만 후보로 조회한다.
- 실제 삭제도 같은 조건을 사용한다.
- `products`와 `user_product_likes`는 조회·삭제 SQL에 포함되지 않는다.
- 운영 로그에는 세션 ID 대신 개수만 출력한다.
- 30분 정리 진입점이 dry-run과 실제 모드 모두에서 AI 작업 정리와 세션 정리를 호출한다.

## AWS 실동작 검증

실제 사용자 데이터 대신 다음 테스트 세션 두 개를 만들었다.

- 만료 세션: 현재보다 1시간 전에 만료
- 유효 세션: 현재보다 1시간 뒤에 만료

검증 시작 상태는 다음과 같았다.

```text
테스트 세션=2
좋아요 행=1
만료 시각 인덱스=1
마이그레이션 표식=1
```

dry-run 결과:

```text
stuck AI 작업=0
만료 아우라딘 세션 후보=1
```

실제 정리 결과:

```text
stuck AI 작업=0
삭제한 만료 아우라딘 세션=1
```

정리 후 DB 직접 확인 결과:

```text
만료 테스트 세션=0
유효 테스트 세션=1
좋아요 행=1
```

검증이 끝난 뒤 유효 테스트 세션도 정확한 테스트 ID로 직접 삭제했고, 테스트 세션 잔여 개수는 `0`이었다.

따라서 AWS에서도 다음 세 가지가 확인됐다.

1. 만료된 세션만 삭제된다.
2. 아직 유효한 세션은 삭제되지 않는다.
3. 별도로 좋아요한 상품은 그대로 남는다.

## 사용자에게 보이는 변화

- 만료 전에는 기존 아우라딘 대화를 계속 이어갈 수 있다.
- 만료 후에는 해당 대화와 임시 추천 목록을 다시 불러오지 못하고 새 추천을 시작한다.
- 이전 대화에서 하트를 누른 상품은 좋아요 목록에 계속 남는다.
- 정상 운영에서는 세션이 만료된 뒤 다음 30분 정리 시점에 삭제된다.
- 예약 작업이 일시적으로 실패하면 다음 성공한 실행에서 밀린 만료 세션을 함께 정리한다.

## 운영 확인 위치

- 로그 그룹: `/ecs/aura-backend-api`
- 정리 로그 접두사: `stuck-cleanup`
- 세션 정리 로그: `[aura:auradin-session-cleanup]`
- 정상 실행 예시: `mode=execute expired=1`

새로운 상시 ECS Worker를 추가하지 않았기 때문에 상시 컨테이너 비용은 늘지 않는다. 기존 30분 유지보수 태스크가 짧은 세션 삭제 쿼리를 하나 더 실행하는 정도만 추가된다.
